# 다국어 일기 학습 앱 설계 (초안, 2026-10-27)

목표: **일기를 쓰는 언어(입력)와 배우는 언어(학습)를 내가 고른다.** 예) 중국어로 쓰고 일본어로 배우기.
핵심 요구: **발음이 자연스럽고, 틀린 것이 최소여야 한다.**

> 이 문서에서 "확인함"은 이 프로젝트에서 직접 실행해 본 것, "자료"는 웹 자료로 본 것, "미확인"은 아직 모르는 것이다.

---

## 1. 언어 설정은 두 가지를 고른다 (확정)
지원 언어는 **일본어, 영어, 중국어, 한국어** 네 가지다.

| 설정 | 뜻 | 예 |
|---|---|---|
| 입력 언어 | 내가 일기를 쓰는 말. **해설도 이 언어로 쓴다** | 중국어 |
| 학습 언어 | 번역해서 배우는 말 | 일본어 |

해설 언어를 따로 고르지 않고 입력 언어를 따른다. 데이터에는 `glossLang`(해설 언어)을 같이 적어 두므로, 나중에 따로 고르게 바꿔도 기록을 고칠 필요가 없다.
번역은 항상 **입력 언어 → 학습 언어로 직접** 한다. 한국어를 거쳐 가면 뜻이 변한다. 조합은 4×3=12가지다.

## 2. 오류를 줄이는 다섯 원칙
1. **역할을 나눈다.** AI는 *의미*(번역, 뜻, 문법 설명)를 맡고, **읽기·단어 나누기·소리는 도구가 맡는다.**
   - 오늘 `了`가 `liǎo`로 나온 사고도 이 원칙을 어긴 데서 생겼다. 단어를 하나씩 따로 계산해서 문맥이 사라졌다. 고친 방식: 문장 전체로 계산한 뒤 단어별로 나눈다.
2. **읽기는 두 경로로 구하고, 다르면 숨기지 않고 표시한다.** (분석 도구 결과 vs AI 결과 → 불일치 시 "확인 필요")
3. **단어 소리는 문장에서 잘라 쓴다.** 단어만 따로 합성하면 문맥 발음이 사라진다(`了` 한 글자 소리 문제).
4. **언어마다 "언어 팩"을 둔다.** 새 언어 = 팩 하나 추가. 앱 본체는 바꾸지 않는다.
5. **정답 모음(골든 테스트)과 등급.** 팩마다 정답을 알고 있는 문장 모음을 두고, 프롬프트·모델·사전을 바꿀 때마다 돌린다. 원어민 검수 전에는 "베타"로 표시한다.

## 3. 전체 흐름
```
일기(입력 언어)
  → 문장 나누기 (앱이 원문 보존)
  → 번역·해설 (AI, 언어 팩의 프롬프트)
  → 검증 층 (아래 4장)
  → 읽기 만들기 (언어 팩의 읽기 도구)
  → 소리 만들기 (문장 합성 + 단어 경계)
  → 화면 (읽기 표시, 따라 읽기, 단어 카드, 퀴즈)
```

## 4. 검증 층 (싼 것부터)
| 층 | 하는 일 | 언제 | 비용 |
|---|---|---|---|
| 0 구조 | 응답 형식, "단어를 이으면 문장과 같다", 읽기 개수 = 글자 수, 출력 문자가 학습 언어 문자인지 | 항상 | 없음 |
| 1 AI 자기 점검 | 애매한 부분을 `확인 필요`로 적게 함 (지금 있음) | 항상 | 번역에 포함 |
| 2 읽기 교차 | 분석 도구 읽기와 AI 읽기를 비교, 다르면 표시 | 항상 | 거의 없음 |
| 3 수준 검사 | 단어 목록(HSK/JLPT/TOPIK/CEFR)으로 범위 밖 단어 표시. **AI가 말하는 급수는 믿지 않는다** (지금 프롬프트에도 "급수 단정 금지" 규칙이 있다) | 항상 | 없음 |
| 4 역번역 | 별도 AI 호출로 "원문 뜻이 보존됐나" 판정 | 표시된 문장, 또는 사용자가 요청할 때 | 호출 +1 |
| 5 사람 | 오류 신고 버튼 → 교정 사전·골든 테스트에 반영. 새 언어는 원어민 검수 후 "검증됨" | 상시 | 사람 |

## 5. 언어 팩이 담는 것
| 항목 | 중국어 (지금) | 일본어 | 한국어 | 영어 |
|---|---|---|---|---|
| 단어 나누기 | AI가 나누고 이은 것이 문장과 같은지 검사. 실패 시 `Intl.Segmenter` | 같은 방식 (형태소 분석기로 대체 가능) | 띄어쓰기 + 조사 분리 | 띄어쓰기 |
| 읽기 | 병음(`pinyin-pro` + 교정 사전, 문장 단위) | 후리가나(형태소 분석기 + AI 교차), 로마자는 선택 | 발음 표기(연음·비음화 등 규칙 기반) | IPA(발음 사전 + 규칙) |
| 소리 | 중국어 음성 | 일본어 음성 | 한국어 음성 | 영어 음성 (미국/영국 선택) |
| 수준 | HSK | JLPT | TOPIK | CEFR |
| 글자 풀이 | 한국어 해설일 때만 한국 한자 훈음 | 한자 훈음/음 | 없음 | 어근·접사(선택) |
| 퀴즈 | 병음 쓰기 | 가나 쓰기 | 한글 쓰기 | 철자 |
| 글꼴 | 한자 세리프 | 일본어 글꼴 + 후리가나 | 한글 | 라틴 |

- **일본어가 가장 어렵다.** 한자 읽기가 문맥에 따라 달라지고(예: 市場 いちば/しじょう), 분석 도구는 가장 흔한 읽기를 고르는 경향이 있다. 자료로는 도구들이 서로 비슷한 수준이고 문맥 의존 읽기가 주된 오류원이라는 점만 확인했고, 도구별 정확도 비교 자료는 **찾지 못했다(미확인)**. → 직접 만든 골든 문장 모음으로 측정해서 고른다.
- 태국어(띄어쓰기 없음), 아랍어(오른쪽→왼쪽), 힌디어(글자 결합)는 화면 구조까지 바뀌므로 **2단계 이후**로 미룬다.
- 추천 순서: 중국어(지금) → 일본어 → 영어 → 한국어(학습용) → 스페인어·프랑스어.

## 6. 자연스러운 소리
1. **문장으로 합성하고 단어 경계로 자른다.**
   - 확인함: 지금 쓰는 `edge-tts 7.3.1`이 중국어·일본어·한국어 모두 **단어별 시작 시각**을 돌려준다 (예: `天气 0.10초`, `突然 0.50초`).
   - 효과 ① 단어 소리가 문맥 발음을 유지한다. ② "따라 읽기" 글자 색 표시를 글자 수 어림 계산이 아니라 **실제 시간**으로 맞춘다. 지금은 어림 계산이라 한두 글자 어긋날 수 있다.
   - 주의: 음성 서비스가 나누는 단어와 우리가 나눈 단어가 다르다(`变冷` vs `变`+`冷`). 글자 위치로 맞춰야 한다.
2. **소리 공급자를 추상화한다.** ① edge-tts(지금, 비공식이라 막힐 위험) ② Azure 음성 서비스(공식, 발음 지정 SSML) ③ 브라우저 음성(예비). 막히면 자동 전환. (미확인: 요금·한도는 도입 전에 공식 가격표로 확인)
3. **애매한 단어만 발음을 지정한다.** Azure 문서상 중국어(zh-CN)·일본어(ja-JP)는 발음을 직접 적어 넣는 태그(`sapi` 또는 `ipa`)를 지원한다(자료). 언어별 지원 범위와 틀린 기호의 처리(오류 400)는 도입 전에 시험해야 한다.
4. 같은 문장·음성·속도는 저장해서 재사용하고, 번역 직후 미리 만든다 (지금 방식 유지).

## 7. 데이터 모델: 모든 기록에 언어 꼬리표
- 일기: `{ srcLang, tgtLang, glossLang, 원문, 번역, … }`
- 단어·문장: `{ lang, text, reading, gloss }`. 단어장 중복은 `(lang, text)`로 구분한다.
- 내 표현 사전: 언어 쌍별로 따로 둔다.
- 필드 이름의 `ko`/`zh`를 `src`/`tgt`로 일반화하고, **기존 데이터는 `zh-Hans`(중국어 간체)로 자동 이전**한다. 이전 후에도 기존 퀴즈·복습·달력이 그대로 동작해야 한다.

## 8. 프롬프트 구조
- 공통 규칙(원문에 없는 내용 금지, 원문 보존, 노트 규칙) + **입력 언어 모듈**(생략된 주어 등 애매함 처리) + **학습 언어 모듈**(수준, 문법 해설 방식, 흔한 함정) + 해설 언어 지시.
- 언어 팩마다 좋은 예시 몇 개와 골든 테스트를 둔다. 지금의 `tests/` 방식을 언어쌍별로 늘린다.

## 9. 내 데이터를 사용자별로 남기는 방법
| 단계 | 방법 | 장점 | 한계 |
|---|---|---|---|
| 지금 | 브라우저 저장(`localStorage`) | 간단, 서버 비용 없음 | 약 5MB. **일기 1편 평균 5.1KB라 약 1000편**(확인함). 기기를 바꾸거나 브라우저 데이터를 지우면 사라짐 |
| 1 | `IndexedDB`로 이동 + 영구 저장 요청 + 백업 알림 | 사실상 한도 없음, 로그인 불필요 | 기기 간 공유 안 됨 |
| 2 | **계정 + 클라우드 동기화** | 여러 기기, 분실 대비 | 아래 참고 |

계정 방식 후보:
- **Supabase**(로그인 + 데이터베이스 + 사용자별 접근 제한 `RLS`): 이메일 링크 로그인을 지원하고, 행마다 `auth.uid()`로 내 데이터만 읽게 막는 것이 표준 방식이다(자료). **동기화 엔진은 기본 제공이 아니다**(실시간 기능은 방송 방식이라 오프라인 동기화를 대신하지 못한다는 자료). 변경분 가져오기·올리기를 직접 만들거나 RxDB 같은 도구를 써야 한다. 무료 한도 수치는 자료마다 달라 **미확인**이다.
- Firebase: 비슷한 구조. 이 프로젝트와 맞는지는 미확인.
- 사용자 구글 드라이브에 저장: 서버 비용이 없지만 로그인 허가 절차가 복잡하다.
- 로그인 없는 "복구 코드": 기기에서 긴 비밀 코드를 만들고 서버에는 그 코드로만 저장. 쉽지만 코드를 잃으면 복구할 수 없다.

계정을 도입할 때 정해야 할 것:
- **일기는 민감한 내용이다.** 서버에 두려면 보관 위치, 삭제 기능, 개인정보 처리방침, 동의 절차가 필요하다(한국 개인정보 보호법 대상 여부는 법률 검토 필요).
- 암호화 저장(서버는 암호문만 보관)도 가능하지만, 비밀번호를 잊으면 복구할 수 없고 서버 검색도 안 된다. 번역할 때 일기가 AI에 전달되는 것은 피할 수 없으므로 이 점은 계속 고지한다.
- 사용자별 번역 횟수 한도(비용·악용 방지).

## 10. 단계별 계획

M1에서 일부러 하지 않은 것: 화면의 `lang="zh-CN"`·한자 글꼴·병음 쓰기 퀴즈 등 중국어에 고정된 약 50곳과 단어장의 중복 기준(지금은 글자만, 언어까지 함께 보게 바꿔야 함). 일본어 화면 없이 바꾸면 한 번도 실행해 보지 않은 코드가 생기므로 M3에서 함께 바꾼다.

| 단계 | 내용 | 끝났다고 볼 기준 |
|---|---|---|
| M0 (이번) | 문장 단위 발음, 글자별 풀이, 내 표현 사전, 일기 보관 한도 확대 | 완료 |
| M1 (완료, 아직 배포 전) | 언어 꼬리표 + 언어 팩 이음새. 서버의 지원 조합·번역 규칙 파일·언어별 음성 목록, 화면의 언어 저장·읽기 만드는 자리·기록 꼬리표·기존 데이터 이전 | **화면 동작이 그대로**. 서버 조합 검사와 화면 이전을 시험으로 확인 |
| M2 (완료) | 소리 개선: 문장 합성 + 단어 경계 | 단어 소리가 문맥 발음, 따라 읽기가 실제 시간 — 실제 시간 시험으로 확인(소리와의 차이 최대 0.18) |
| M3 (완료, 배포 전) | 일본어 팩(베타): 후리가나 두 경로 확인, 문맥 읽기 목록, 골든 문장 | 골든 문장에서 읽기 오류율·불일치 표시율을 **측정해서 기준을 정함** |
| M4 | 설정에 입력 언어·학습 언어 선택 | 같은 일기를 언어쌍을 바꿔 학습 가능 |
| M5 | 계정·동기화 (위 9장 2단계) | 새 기기에서 로그인하면 일기·단어가 그대로 보임 |

정확도 목표(예: 읽기 정확도 99%)는 **측정 전에는 정하지 않는다.** M3에서 골든 문장 모음으로 현재 수준을 먼저 재고 정한다.

## 11. 아직 모르는 것
- 일본어 읽기 분석 도구별 정확도 (직접 측정 필요)
- Azure 발음 지정의 언어별 지원 범위와 요금
- edge-tts의 장기 안정성 (비공식 서비스)
- 언어별 AI 번역 품질 편차 (사용자가 적은 언어일수록 낮을 수 있음 → 원어민 검수)
- 수준별 단어 목록과 발음 사전의 사용 허가 조건 (JLPT는 공식 단어 목록이 없고, 악센트 사전은 사용 조건이 제각각)
- 번역 + 글자 풀이 + 검증까지 합친 호출 비용
