# 작업 카드 방식 (기능 하나 = 카드 한 장 = 새 대화 하나)

목적: 대화가 길어지면 앞 내용을 놓치고 토큰이 늘어난다. 기능마다 새 대화로 시작하고, 이어 가는 데 필요한 모든 것을 **카드 파일**에 적어 둔다.

## 진행 순서 (여기가 현황판 — 끝나면 상태만 바꾼다)
| 카드 | 내용 | 상태 |
|---|---|---|
| T1 | 후리가나를 한자 덩어리 위에 한 번에 + 입력 언어 중립 문구 | 완료(미확인: 휴대폰 화면) |
| T2 | 단어 소리 자르기 보정(앞 소리가 섞이는 문제) | 완료 |
| T3 | 읽기가 애매한 한자를 히라가나로 바꿔 음성 합성(市場 오독 등) | 완료 |
| T4 | 듣기 비교 페이지로 음성 고르기(무료 음성만) | 완료 |
| T5 | 일본어 글자별 풀이 | 완료(사용자 확인 2026-10-27) |
| 이후 | 일본어 퀴즈 끝까지 시험, 휴대폰 확인, 배포 승인 후 배포(`CLAUDE.md`의 배포 규칙) | 미정 |

## 새 대화 시작 문장 (사용자가 그대로 붙여 넣는다)
```
01.program/chinese-diary 폴더의 CLAUDE.md와 design/tasks/README.md를 읽고, 현황판에서 "대기"인 첫 카드를 진행해줘.
```

## 한 카드의 진행 규칙 (Claude가 지킨다)
1. **읽는 것은 CLAUDE.md → 이 README → 해당 카드 한 장**뿐. 코드는 카드에 적힌 `grep` 단어로만 찾아 읽는다(통째로 읽지 않는다). 카드에 없는 큰 결정이 필요하면 사용자에게 먼저 묻는다.
2. 시작하면 카드 상태를 `진행 중`으로 바꾸고, `backup/index_<이름>_vN.html`(현재 v19 다음 번호)으로 이전 버전을 보관한다.
3. 카드의 **완료 기준**을 하나씩 시험으로 확인한다. 시험은 **분리 서버**로만 한다(데이터 안전 규칙). 사람이 귀·눈·휴대폰으로 확인할 항목은 "확인하지 못했다"고 적고 사용자에게 요청한다.
4. 끝나면: ① 카드에 `결과` 칸(한 줄 요약+수치) 기록 ② 현황판 상태를 `완료(미확인: …)`로 ③ `README.md` 개편 이력 한 줄 ④ 로컬 커밋 ⑤ **사용자에게 "이 카드 끝. /clear 후 시작 문장을 다시 붙여 넣으세요"라고 알린다.** 한 대화에서 다음 카드로 넘어가지 않는다.
5. 카드가 한 대화에 너무 크다고 판단되면(코드 수정 3곳 이상 + 시험이 길어짐) 중간에 카드를 둘로 쪼개 현황판에 적고 첫 번째만 끝낸다.
6. 결정 사항: **유료 음성·유료 서비스는 쓰지 않는다**(사용자 결정, 2026-10-27). 앱 화면 언어는 한국어로 둔다.

## 공통 시험 도구 (모두 `tests/`, git 제외 폴더)
- 분리 서버: `CHINESE_DIARY_DATA_DIR=/private/tmp/claude-501/trydata PORT=3002 node app/server.js` (끝나면 `pkill -f app/server.js`)
- 화면: `PRESET='{"intro-seen":"\"1\"","lang-tgt":"\"ja\""}' SHOT=/경로/x.png node tests/browser_check.js http://localhost:3002/ <스크립트>` — `PRESET`은 localStorage 미리 넣기(값은 JSON 문자열), `SHOT`은 스크린샷. 샘플 번역 결과 `tests/ja/sample_result.json`을 `app/public/`에 임시로 복사해 `fetch`로 불러 `render()`에 넣는 방식은 `tests/ja/ui_render_check.js` 참고(끝나면 복사본 삭제, `git status`로 확인)
- 소리 측정: `tests/ja/tts_offset_check.py`(경계 시간 vs 실제 소리), `tests/ja/tts_reading_check.py`(한자를 어떻게 읽는지, 소리 파형 거리). 분리 서버를 켠 뒤 실행. macOS `afconvert` 사용
- 일본어 읽기 정확도: `tests/ja/golden.js`(정답 25문장), `kuromoji_check.js`, `ai_reading_check.js`
- 화면 문법 점검: `<script>` 블록을 합쳐 `node --check`

## 이미 알고 있는 사실 (카드마다 다시 조사하지 않는다)
- 일본어 번역·읽기는 서버가 `ja` 키를 화면용 `zh` 키로 바꿔 보낸다(`app/ja_reading.js`). 단어에는 `reading`(히라가나 AI)·`check`/`kuro`(분석 도구와 다를 때)가 있다.
- 화면은 "한 글자 = 한 칸(`.c`)" 구조이고 따라 읽기(`karLineFor`, `karBegin`)·형광펜·문장 속 단어 위치(`ctx_i`)가 이 구조에 기대고 있다. 일본어 읽기 토큰은 글자 수와 같게 만든다(`jaCharTokens`, `jaSplit`, `wordTokens`).
- 소리: 서버 `makeSpeech`+`tts_worker.py`(edge-tts), 단어 경계 `/api/tts-timing`, 화면 `charTimes`·`speakSegment`(문장 소리에서 단어 구간만 재생). 일본어 음성은 나나미·케이타 2종뿐.
- 측정 결과(2026-10-27, README 참고): 경계 시간은 실제 소리보다 시작 약 100~200ms 일찍, 끝 약 55~175ms 늦다. 한자 읽기는 二日·一人·大人는 맞고 市場는 「しじょう」로 읽어 틀리며 十分·日本人은 불분명.
